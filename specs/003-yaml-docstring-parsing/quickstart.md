# Quickstart: YAML Docstring Parsing

**Branch**: `003-yaml-docstring-parsing` | **Date**: 2026-09-11 | **Plan**: [plan.md](plan.md)

This is a runnable validation guide for the feature. It proves the tool
interprets docstrings as YAML and extracts documentation data from them
end-to-end (parse → extract → generate HTML). Implementation details live in
`tasks.md` and the implementation phase.

## Prerequisites

- Rust stable toolchain (`rustc`, `cargo`) installed via
  [rustup](https://rustup.rs/).
- A sample Python package with YAML-structured docstrings (use
  `demo/demo_2.py` as a structural reference).

## Setup

```bash
# From the repository root
cargo build
```

## Building the documentation for a sample package

Given a sample package such as:

```text
samplepkg/
└── utils.py
```

Run the generator:

```bash
cargo run -- <input_dir> <output_dir>
# e.g.
cargo run -- samplepkg ./docs-output
```

Expected outcome: an HTML site is written to `./docs-output` containing an
entry for every module, class, and function, each identified by its full
Python package import path, with a navigation index.

## Validation scenarios

### 1. YAML-structured docstrings (SC-001, SC-002, SC-003, FR-001, FR-003)

- Give `utils.py` YAML docstrings with `description`, `args`, `returns`, and
  `raises` keys on a module, a class, and a function (mirror the structure in
  `demo/demo_2.py`).
- Run the generator.
- **Expected**: The HTML site contains entries for each documented element
  with their description, argument list, return value, and raised exceptions,
  matching the YAML values field-for-field.
- **Acceptance scenario from spec**: `Given a module, class, or function whose
  docstring contains a YAML mapping with description, args, returns, and
  raises keys, When the generator runs, Then the generated documentation shows
  the description, each argument with its description, the return value, and
  each exception with its description, matching the values in the YAML.`

### 2. Plain-prose docstrings (FR-010)

- Give one element a plain-prose docstring with no YAML keys (no colons), e.g.
  `"""Formats text for display."""`.
- Run the generator.
- **Expected**: The element is documented with the prose as its description;
  no `args`/`returns`/`raises` sections appear.

### 3. Undocumented elements (FR-008)

- Leave one function with no docstring.
- Run the generator.
- **Expected**: The function still appears in the HTML, with an
  existence-only entry (name and path, no extra description).

### 4. Malformed / invalid YAML docstrings (FR-007, SC-004)

- Give one element a docstring that fails YAML parsing (e.g. a legacy
  JavaDoc-style `@arg x input` line, or an `args:` key whose value is a string
  instead of a list).
- Ensure another element is documented correctly.
- Run the generator.
- **Expected**: The run completes (does not fail). The malformed element's
  entry shows an error message stating the docstring was not written correctly
  or could not be interpreted; the correctly documented element still has full
  documentation.
- **Acceptance scenario from spec**: `Given a docstring that fails YAML
  parsing, When the generator runs, Then the affected element's entry displays
  an error message ... the run completes and all other properly documented
  elements render normally.`

### 5. Unknown-key tolerance (spec edge case)

- Include an `example:` block and a `returns.type` in one of the YAML
  docstrings (as in `demo/demo_2.py`).
- Run the generator.
- **Expected**: The run succeeds; only the recognized keys
  (`description`, `args`, `returns.description`, `raises[].type/description`)
  are extracted, and the extra keys have no effect on output.

### 6. Determinism (FR-006, SC-005)

- Run the generator twice on unchanged input.
- **Expected**: Byte-for-byte identical output.

## Boundary inputs

- Empty directory / directory with no Python files: completes with an empty
  or minimal site and no crash.
- Non-existent input path: useful error, no crash.
- Prose containing a colon and space (e.g. "Returns: a string."): the text may
  parse as a YAML mapping of unknown keys; the entry then has no description.
  This is a documented authoring risk (see the docstring-syntax contract).
